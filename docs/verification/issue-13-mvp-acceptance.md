# Issue #13：MVPの結合・長時間稼働の実機確認

## 範囲と状態

MVP v0.1の受入確認として、Raspberry Pi実機の本番構成で、機能・視認性・起動と復旧・時刻・通信とキャッシュの異常系・72時間の連続稼働を確かめた結果を記録する。進め方と判定の規則は、[Issue #13の方針コメント](https://github.com/rinYamano211/home-digital-signage/issues/13#issuecomment-7090369824)と[技術スタック選定 第27章](../technology-stack.md#long-run-observation)に従った。

- 確認日：2026-11-23〜2026-11-26
- 対象：Release `20261123-134710-6ed6fe8`（`main`の`6ed6fe8`、PR #137）。段階0では`20261123-125433-d69c1e5`をDeployしたが、段階2で計測の不足が見つかったため、PR #137をDeployし直して、このReleaseに固定した。72時間試験の間はDeployしていない
- 環境：Raspberry Pi 5、Debian 13（trixie）・ARM64、Kernel 6.18.50+rpt-rpi-2712、systemd 257、Chromium 155.0.8059.79、Node.js v24.22.1。RTCのバックアップ電池なし
- **状態：段階0〜5を実施した。** 結果の判断（MVP v0.1として日常利用できるか）と、Issueのチェック欄の更新は、ユーザーが行う。実機で確かめていない事項は「確認していない事項」に残す
- Secret・地点・カレンダーID・予定のタイトルの値は記録しない

## 方法

- **Piの操作は、ユーザーの依頼でClaude CodeがSSHで行った。** これまでの検証記録（#12等）では、ユーザーが手動で操作し、Claude CodeはPiを操作していなかった。今回の分担は次のとおり。
  - Claude Code：開発PCからSSHで、確認のコマンド・Script（Piの`~/incoming`に置いた）を実行した。`sudo`が必要な操作は1つのScriptにまとめ、Terminalで実行した
  - ユーザー：SSHの鍵の登録と`sudo`のパスワードの入力（Claude Codeはパスワードを扱っていない）、電源・カレンダーの共有の操作、画面の目視、Deploy・障害の注入等の承認
- 計測：60秒ごとの計測（rootのsystemd timer、`scripts/collect-metrics.sh`）と、5分ごとの描画の確認（`signage`のユーザーtimer、`scripts/check-render.sh`）。CSVは計測用ディレクトリに置き、Repoには入れない。項目と判定の規則は[27.3〜27.8](../technology-stack.md#long-run-observation)を参照
- 時刻は特に書いていなければJST。NTPの同期で壁時計が飛ぶ段階3では、journalの単調時計（起動からの秒）とCSVの`uptime_s`で比べた

## 段階0：準備

- Deploy：`npm ci --omit=dev`は成功。`better-sqlite3`のinstall scriptが`allowScripts`の対象外という`npm warn`が出たが、Pi用のビルド済みファイルを同梱しており、DBは使えている（`/api/published-states`の200、計測の`states_result=OK`）。実害はないと判断した
- 基準値：DB 237,568バイト、journal 16M、Backend・Kioskの`NRestarts`は0、`/`の空き46G
- 60秒の計測：`systemd-analyze verify`はエラーなし。`script_ms`は通常約400ms、10分ごとの項目（PSS・journalの大きさ）を取る回で約450〜950ms。`ERR`を含む行は0
- `grim`：導入済み。1回の撮影は74ms（CPU時間65ms）。撮った画像は開かずに消した。**最大メモリは測れなかった**（`/usr/bin/time`がない）
- 描画の確認：5分ごとに`CHANGED`を記録。画像は残っていない

確認用の予定を4件登録した（終日、進行中、これから、23:30〜翌00:30）。本番のKioskと実データで、ユーザーが目視した。照明は昼の自然光で、映り込みは気にならなかった。

| 項目                                                                     | 結果                                     |
| ------------------------------------------------------------------------ | ---------------------------------------- |
| 時計・日付・曜日、今日の予定、今日の天気、週間天気                       | PASS                                     |
| 「今日の予定→今日の天気→週間天気」の順の自動切替、切替中も時計が常時表示 | PASS                                     |
| 時計を約3mから判読、現在の天気・気温の概要を約3mから把握                 | PASS（時計や大きい文字は3m以上で読めた） |
| 詳細情報（予定・時間別・週間）を意識して見れば読める                     | PASS（小さい文字は約2mで読めた）         |

- 時計の文字の大きさ：200px（現行）と210pxを、検証用Build（合成データ）で3mから比べた。**あまり差はなく、MVPとしては200pxで十分見えるため、変更しない**（ユーザー）。210pxでも時計は枠に収まり、ほかの領域と重ならなかった。比較の間（約3分）は本番のKioskを止めていた。72時間試験の前の操作である
- 将来、時計の主張をもっと大きくしてもよい、というユーザーの所感があった（範囲外。UIの改善として別に検討する）

## 段階2：起動・復旧

[#12の検証記録](issue-12-autostart.md)で確かめた次の項目は、再実施していない：電源投入から基本画面まで実測20秒（P8）、Chromium主Process・Backendの異常終了から約5秒・約6秒で復旧（P9）、自動起動・再起動後の自動起動・外部データを待たない起動（P5・P8・P11・P15）。

### Backendの停止と起動

Deployの切替（`systemctl restart`）のjournalから：停止の開始から`Stopped`まで約0.4秒（Backendの猶予10秒・`TimeoutStopSec=15s`に収まる）。起動から`startup_complete`まで約0.8秒。

### 設定の維持

再起動の後も、天気・予定・降雨のProviderが登録され（`*_provider_enabled`）、5つのStateの取得が`success`になった。ConfigとSecretは再起動の後も維持されている。

### Chromiumのレンダラーだけを落とす：自動では復旧しない

- Kiosk Unitのcgroupのレンダラー（`--type=renderer`）の1つに、ユーザーの承認を得て`SIGKILL`を送った
- 画面は**エラーの表示（エラーコード9）のまま**で、約2分半後も戻らなかった。主Processは生きているため、Kiosk Unitは`active`・`NRestarts=0`で、systemdは再起動しない。新しいレンダラーも作られなかった
- `systemctl --user restart home-digital-signage-kiosk`で戻した
- 描画の確認（5分ごと）は、このエラーの表示の間を撮っていない（間隔より短い停止は検出できない例）
- **#13では直さず、別Issueの候補とする**（レンダラーだけのCrashからの自動復旧）

### 計測の不足と修正

Chromiumの主Processは、起動の後に自分を別のcgroup（`app-org.chromium.Chromium-<PID>.scope`）へ移す。そのため、計測のChromiumの値に主Process（RSS約315MB）が入っていなかった。PR #137で、計測と[27.4](../technology-stack.md#long-run-observation)の定義を直し、Deployし直した。直した後は`chromium_procs`が11→12、`chromium_rss_kb`が約86万→約116万になった。

## 段階3：時刻（電源断と起動直後のオフライン）

[#108](https://github.com/rinYamano211/home-digital-signage/issues/108)の手順1（[#65](issue-65-time-availability.md)のV4・V5の本番版）。Wi-Fiを切った状態で電源を約6分抜き、起動の5分後にWi-Fiが戻る一時的なUnitを置いた（試験の後に削除した）。

| 起動からの時間 | 事象                                                                                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| +9.9秒         | `time_availability_changed`：`unavailable`（`ntp: unsynchronized`、`rtc: invalid`）。画面は「時刻を合わせています」と「時刻を確認できるまで」の表示 |
| +300.4秒       | Wi-Fiが戻った                                                                                                                                       |
| +316.6秒       | NTPの初回同期。起動直後の時計は、電源を切った時刻付近から始まっており、同期で約7分進んだ                                                            |
| +319.9秒       | `available`（`reason: ntp`）。同期から3.3秒                                                                                                         |
| 同期から約13秒 | 画面が時計と予定・天気の表示に戻った（ユーザー）                                                                                                    |

- 同期の後の最初の取得：予定約53秒・現在の天気約56秒（予定の時刻を過ぎていた。60秒以内の再評価で取得）、時間別約3分（予定どおり）、降雨約5分25秒（Clock Trustの回復より前には送っていない）、週間は次の予定の時刻（16:36）に試行された（段階4cで確認）
- `scheduler_held`・`scheduler_recheck_deferred`は出なかった

| 項目                                                            | 結果 |
| --------------------------------------------------------------- | ---- |
| System Timeが使えないとき、誤った時刻を通常の時計として出さない | PASS |
| 使えるようになった後、操作なしで通常の時計へ移る                | PASS |
| 同期の後、操作なしで各Stateの取得が再開する                     | PASS |

時計の遅れは約7分で日付をまたがないため、「前日の予定・期限切れの天気を出さない」は、この試験では起こり得ない（確認の対象外）。

## 段階4：通信・キャッシュ・異常系

障害は、Wi-Fiの無効化と`/etc/hosts`の書換え（対象のホストを`127.0.0.1`・`::1`へ向ける）で入れた。元に戻す操作は、一時的なtimer（`systemd-run`。再起動すると消える）で予約した。`/etc/hosts`は複製から戻し、`cmp`で元と一致することを確かめた。試験の後、一時的なUnit・timerと複製は残っていない。

### 4a Wi-Fi断（22分）

- 断の間、全Stateが失敗（`network_error`）を続け、APIの`dataSource`は`cache`になった（[#87](https://github.com/rinYamano211/home-digital-signage/issues/87)）
- 画面：時計が進み、巡回は続いた。約15分後、予定・今日の天気に「更新待ち」の札と最終更新の時刻（`HH:MM時点`）が出た。降雨帯は予報が隠れて「更新待ち」になった
- Wi-Fiが戻った後の復旧：降雨12秒、予定40秒、現在の天気42秒、時間別2分44秒（[#113](https://github.com/rinYamano211/home-digital-signage/issues/113)）。札は約3分以内にすべて消えた

### 4b 降雨だけ遮断（`api.tomorrow.io`、約32分）

- 降雨だけが`failure`・`cache`になり、ほかのStateは`success`のまま
- 画面：降雨帯だけが「更新待ち」になった。最後の成功から30分（`expiresAt`）を過ぎると、APIの`data`が`null`になり、降雨帯は「雨の予報を取得できません」になった（[#93](https://github.com/rinYamano211/home-digital-signage/issues/93) D-4）
- 解除の後、約4分（Backoffの次の試行）で`success`に戻り、降雨帯も戻った

### 4d 認証エラー（カレンダーの共有を外す、4bと同じ時間帯）

- ユーザーがサイネージのカレンダーの共有からService Accountを約10分外し、戻した
- ログに`schedule_acquisition_failed`（`reason: forbidden`）が2回出た。同じ時間帯の降雨の失敗（`network_error`）と区別できる
- 画面は予定が「更新待ち」。画面では理由を区別しない設計（[UI設計 6.6](../ui-design.md)）
- 共有を戻した約1分後に`success`に戻った

### 4c 天気だけ遮断（`api.open-meteo.com`、約2時間）

- 現在・時間別・週間が`failure`・`cache`になった。予定・降雨は`success`のまま
- 週間天気の定時の試行（16:36）が失敗し、期限内（12時間）のキャッシュで表示が続いた。画面に「更新待ち」の札が出た（[#9](issue-9-weather.md) C1の引継ぎ）
- 現在・時間別は最後の成功から2時間（`expiresAt`）を過ぎると`data`が`null`になり、今日の天気の該当部分だけが「取得できません」になった。予定と週間天気は表示が続いた
- 解除の後、時間別・週間・現在の順に約2・4・5分で`success`に戻り、札がすべて消えた

### 4e 初回取得失敗（キャッシュなし）

本番のDBに触れずに再現する方法がないため、実機では行わなかった（ユーザーの判断）。検証用Build（合成データの「一度も取得できない」状態）、[#10](issue-10-schedule.md)のE4、CIのテストで代える。

### 失敗の件数

14:30〜17:52の警告は、天気85件・予定8件（`network_error` 6件・`forbidden` 2件）。すべて障害を入れていた間だけで、Backend・Kioskの再起動はなかった。

計測のtimerと描画の確認のtimerを停止・無効化した（[運用手順書 5.4](../operations.md)）。Unit・Scriptのファイルは残した。計測用ディレクトリを消すかは、ユーザーが判断する。
