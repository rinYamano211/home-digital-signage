### 再起動後の待機（確認した制限）

再起動後の最初の取得は、約70分後だった。2回の再起動で同じ結果になった。

| 再起動（JST） | 最初の予約（JST） | 経過   | 備考                                                   |
| ------------- | ----------------- | ------ | ------------------------------------------------------ |
| 15:06:04      | 16:16:04          | 約70分 | 旧履歴が20件以上あった                                 |
| 18:07:08      | 19:17:09          | 約70分 | 予約番号37。`consecutiveFailures`は0。次回取得19:22:08 |

- これは、設計（[technology-stack.md](../technology-stack.md) D-03「旧履歴の保守的な計上」）どおりの動作である。再起動のたびに、旧履歴を全件その窓へ計上し、窓ごとの待機（1秒窓=1分、60分窓=65分、24時間窓=25時間）が終わるまで取得を抑止する。待機は再起動をまたいで引き継がない。待機の完了後の再開は、5分周期のRecoveryの再確認に合わせるため、約70分になる。
- 旧履歴が20件以上あると60分窓が上限（20件）に達し、約65〜70分取得できない。400件以上（約33時間の稼働）では、24時間窓が上限に達し、約25時間取得できないと、コードからは読み取れる。**25時間の影響は推定で、実機では観測していない。**
- 旧履歴が20件未満のとき（約100分未満の稼働後）は、60分窓は止まらない。13:30ごろの再起動では、再開まで約10分（Gate・Clock Trustの再開待ち）だった。
- 影響を受けるのは降雨（Tomorrow.io）だけである。Schedule・Open-Meteoの3つは、Quotaの対象外で影響しない。降雨帯は、取得できなくなってから10分で更新待ち、30分で「取得できません」になる。
- この制限は仕様として受け入れた（方針A）。#13の72時間試験では、予期しない再起動（クラッシュ・更新・設定変更）で降雨が欠測する可能性がある。時刻ベースで旧履歴を評価する案（案C）は採用しておらず、Issueも作成していない。
