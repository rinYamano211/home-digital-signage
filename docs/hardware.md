# Hardware Design

## 1. 目的

Home Digital Signage に必要なハードウェア構成を決定する。

本ドキュメントでは、要求からハードウェア選定条件を導出し、候補調査・比較・採用判断を記録する。
単なる製品一覧ではなく、**論点 → 選択肢 → 判断 →
理由**を追跡できることを重視する。

------------------------------------------------------------------------

## 2. 要求・要件の整理

### 2.1 背景

初期検討では、以下のような内容が混在していた。

- 実現したい機能
- 性能・品質
- ハードウェア
- 将来構想
- 技術的な実現手段
- 学習目標
- 開発方針

そのため、製品選定の前に目的と手段を分離し、以下へ分類した。

- 機能要件
- 非機能要件
- ハードウェア要件
- 拡張要件
- 監視要件
- 制約条件
- 学習目標
- 開発方針

### 2.2 フェーズの定義

| フェーズ         | 定義                                 |
|------------------|--------------------------------------|
| **MVP**          | サイネージとして成立する最小構成     |
| **v1.0**         | 自宅に壁掛けして日常利用できる完成版 |
| **Future**       | v1.0 完成後の拡張                    |
| **Out of Scope** | 今回のプロジェクトでは実装しない     |

「必須」と「MVP」は同義ではない。

将来実装する機能であっても、後から追加できないハードウェア上の制約については
MVP の選定段階から考慮する。 例えばセンサー機能自体は Future だが、GPIO
等の拡張手段は初期ハードウェア選定時から確保する。

### 2.6 拡張要件

拡張機能を MVP で実装する必要はないが、**拡張不能な MVP にはしない**。

| 拡張要件                             | 実装時期 | MVP 時の考慮事項                         |
|--------------------------------------|----------|------------------------------------------|
| コンテンツを追加しやすくする         | Future   | コンテンツ追加が極端に難しい構造にしない |
| クラウドと通信できる                 | Future   | 将来通信処理を追加できる構成にする       |
| クラウドから設定・写真を管理する     | Future   | ローカル実装へ強く依存しすぎない         |
| 温湿度・照度・人感センサーを追加する | Future   | GPIO 等の接続手段を確保する              |
| 自動輝度調整                         | Future   | センサー追加や画面制御を妨げない         |
| カメラ機能                           | Future   | カメラ接続インターフェースを確保する     |
| 画面の自動 ON/OFF                    | Future   | 将来画面制御を追加できる余地を残す       |
| 遠隔から状態確認・再起動             | Future   | ネットワーク接続やログ取得を可能にする   |

| 監視要件                      | フェーズ | 方針                                       |
|-------------------------------|----------|--------------------------------------------|

| 制約条件                                 | 適用範囲             | 方針                                             |

| 可能な限り初期費用を抑える               | **プロジェクト全体** | MVP に不要な機器は必要になった段階で追加する     |
| クラウド利用料をできるだけ抑える         | **プロジェクト全体** | 無料枠・低コストサービスを優先する               |
| 自宅で利用する                           | **プロジェクト全体** | 家庭内の日常利用を前提とする                     |

## 3. ハードウェアに必要な条件

要件から、ハードウェア選定へ直接影響する条件を抽出する。

| 選定観点           | 元になる要件・条件           | ハードウェア選定で確認すること                                  |
|--------------------|------------------------------|-----------------------------------------------------------------|
| **映像出力**       | ディスプレイへ映像出力       | 希望するディスプレイへ安定して出力できるか                      |
| **処理性能**       | Web UI の日常利用            | Web UI・ブラウザ・コンテンツ切替を問題なく処理できる CPU/RAM か |
| **ネットワーク**   | Wi-Fi・外部データ取得        | Wi-Fi を標準搭載しているか                                      |
| **画面サイズ**     | 掛け時計程度                 | 想定する壁掛けサイズに合うか                                    |
| **視認性**         | 2〜3m 程度から確認           | サイズ・解像度・輝度・視野角が適しているか                      |
| **外観**           | 家庭内で壁掛け               | ベゼル等が完成品の外観を大きく損なわないか                      |
| **重量**           | v1.0 で壁掛け                | Pi・Display・筐体等を含めて現実的な重量にできるか               |
| **厚み**           | 壁掛け一体型                 | Pi・冷却・配線を含めた筐体を過度に厚くしないか                  |
| **長時間稼働**     | 常用                         | 長時間利用に適した構成か                                        |
| **冷却**           | CPU 温度・長時間稼働         | ファン等を利用し、筐体内でも吸排気を確保できるか                |
| **ストレージ**     | OS・アプリ・ログ・キャッシュ | 容量・耐久性・方式が適切か                                      |
| **音声**           | Future の音声機能            | HDMI / USB / Bluetooth 等の出力経路を確保できるか               |
| **拡張 I/O**       | センサー等                   | GPIO・USB 等を利用できるか                                      |
| **カメラ拡張**     | Future のカメラ              | 接続インターフェースを確保できるか                              |
| **電源**           | 安全な長時間給電             | 必要電力・AC アダプタ・配線を考慮できるか                       |
| **筐体への組込み** | v1.0 の専用筐体              | 寸法・端子位置・冷却・固定方法が筐体設計を妨げないか            |
| **予算**           | HW 全体 5〜6 万円            | 全部品を含めて予算内か                                          |

### 完成形の基本方針

賃貸住宅で使用するため、壁への加工を可能な限り少なくする。

ディスプレイ単体を壁へ固定するのではなく、

``` text
正面
┌──────────────────┐
│      Display     │
└──────────────────┘

側面
Display
  │
  ├─ Raspberry Pi 5
  ├─ Active Cooler
  ├─ 内部配線
  └─ 背面カバー
        │
        └─ 軽量な壁掛け方法
```

のように、**Display + Raspberry Pi + 冷却機構 +
配線を一体化した筐体**を作成し、完成品全体を壁掛けする方針とする。

そのため VESA 対応そのものより、

- 完成品の重量
- 完成品の厚み
- Pi との一体化
- 冷却
- 配線処理
- 外観

を重視する。

## 4. Raspberry Pi 本体の選定

### 4.1 選定条件

- Web UI を日常利用に支障なく動作させられること
- OS・ブラウザ・アプリを同時実行できるメモリ容量
- 十分な映像出力能力
- Wi-Fi / Bluetooth
- GPIO
- カメラ接続
- USB 等の周辺機器拡張
- 音声出力手段
- 長時間稼働可能な冷却構成
- 壁掛け筐体へ組み込めるサイズ・重量
- 消費電力・電源要件
- プロジェクト予算を過度に圧迫しないこと

### 4.2 候補

- Raspberry Pi 5
- Raspberry Pi 4 Model B
- Raspberry Pi Zero 2 W

### 4.3 Pi 4 / Pi 5 の比較結果

Pi 5 は Pi 4 と比較して CPU および Web
ブラウザ関連の処理性能に余裕がある。

本プロジェクトでは Chromium 等を利用して Web UI
を常時表示する予定のため、この性能差は実際の画面表示・将来拡張に対する余裕につながる。

一方、Pi 4 / Pi 5
ともに冷却なしの高負荷状態では温度上昇が大きいため、採用モデルにかかわらず冷却を行う方針とした。

Pi 5 には専用ファンコネクタがあり、GPIO
を冷却ファン用に消費せずに済む点も評価した。

### 4.4 RAM 容量

| RAM      | 今回の用途での評価                           |
|----------|----------------------------------------------|
| 1GB      | OS + Chromium + Web UI では余裕が少ない      |
| **2GB**  | MVP の想定処理では現実的                     |
| 4GB      | 余裕は大きいが、現時点では必要性が明確でない |
| 8GB 以上 | 今回の用途では過剰                           |

MVP では主に以下を動作させる。

``` text
Raspberry Pi OS
├─ Linux / system processes
├─ Chromium
│  └─ Signage Web UI
├─ API data acquisition
└─ logs / cache
```

2GB と 4GB の価格差に対し、現時点で 4GB
を必要とする明確な処理がないため、将来の不確実性だけを理由に増量しない。

**必要量を仮定し、実装後に実測して検証する**方針とする。

### 4.5 採用

**Raspberry Pi 5 2GB**

### 4.6 採用理由

1.  Web サイネージとして十分な処理性能を期待できる
2.  GPIO・USB・カメラ等の将来拡張手段を確保できる
3.  専用ファンコネクタにより冷却構成を取りやすい
4.  常時高負荷用途ではないため、Pi 5 の消費電力増加は許容できる
5.  2GB は MVP に必要十分と仮定でき、4GB への増額根拠が現時点では弱い
6.  Pi 5 の性能・拡張性と価格のバランスがよい

### 4.7 実機検証事項

MVP 実装後に以下を確認する。

- `free -h` 等による RAM 使用量
- `htop` 等による CPU / RAM 使用状況
- Swap 使用量
- OOM の有無
- CPU 温度
- 長時間稼働時の安定性

2GB で余裕が不足する場合は、その結果を今後の構成判断へ反映する。

### 4.8 不採用候補

#### Raspberry Pi Zero 2 W

小型・低価格・低消費電力という利点はあるが、

- GPIO 利用にヘッダーピンのはんだ付けが必要になる構成がある
- 512MB RAM で Web ブラウザ等を含む構成の余裕が小さい
- 将来のセンサー・カメラ・クラウド連携を考えると性能余裕が小さい

ため不採用とした。

#### Raspberry Pi 4 Model B

今回の用途でも利用可能な候補ではある。

ただし、Pi 5 との本体価格差に対して、

- Web / CPU 性能
- 将来の性能余裕
- 専用ファンコネクタ
- ストレージ等の拡張余地

を評価し、Pi 5 を採用した。

## 5. 冷却方式の選定

### 5.1 冷却に求める条件

| 選定観点               | 条件                                 |
|------------------------|--------------------------------------|
| 長時間稼働             | サイネージとして長時間連続稼働できる |
| サーマルスロットリング | 通常運用で可能な限り発生させない     |
| Pi 5 対応              | Pi 5 で安定利用できる                |
| 厚み                   | 壁掛け一体型を過度に厚くしない       |
| 重量                   | 完成品の軽量化を妨げない             |
| 筐体組込み             | Display 背面へ収めやすい             |
| エアフロー             | 背面筐体を付けても吸排気を設計できる |
| 静音性                 | 家庭内で常時動作しても気になりにくい |
| 制御                   | 必要なときにファンを制御できる       |
| GPIO                   | 将来のセンサー用 GPIO を極力妨げない |
| 価格                   | 総予算内に収める                     |

### 5.2 比較した方式

| 方式                           | 今回との相性 |
|--------------------------------|--------------|
| 冷却なし                       | △            |
| ヒートシンクのみ               | ○            |
| **Raspberry Pi Active Cooler** | **◎**        |
| Raspberry Pi 5 Case + Fan      | △            |
| 大型クーラー                   | △            |
| 放熱筐体                       | △            |

### 5.3 採用

**Raspberry Pi Active Cooler**

### 5.4 採用理由

- Raspberry Pi 5 用として構成しやすい
- ヒートシンク + ファンによるアクティブ冷却
- Pi 5 の専用ファンコネクタを使用できる
- PWM 制御が可能
- 一体型筐体へ組み込みやすいサイズ
- 約 1,000 円台で導入でき、総予算への影響が小さい

調査時点の参考情報：

- 秋月電子：約 1,100 円
- 最大回転数：8,000 RPM
- 最大風量：1.09 CFM
- Pi 5 + Active Cooler の実測例：約 71g

### 5.5 筐体設計への要求

Active Cooler を覆う背面カバーを作る場合、

``` text
Display
████████████████
      │
     Pi 5
 ┌───────────┐
 │ Active    │
 │ Cooler    │
 └───────────┘
      ↑
   吸気空間

──────────────
   背面カバー
      ↓
    排気口
```

のように、

- Active Cooler 上部の吸気空間
- 吸気口
- 暖気を逃がす排気口

を確保する。

薄さだけを優先して Active Cooler の吸排気を妨げない。

### 5.6 将来拡張時の注意

HAT は形状によって Active Cooler
のヒートシンク等と物理干渉する可能性がある。

HAT 利用は Future
のため、追加時に干渉・スペーサー・冷却構成を再評価する。

## 6. ディスプレイの選定

### 6.1 選定条件

当初は高解像度を強く重視していたが、実際の設置距離・外観・一体型筐体という完成イメージを検討する中で条件を更新した。

- 厚み

## 7. ストレージの選定

### 7.1 ストレージに求める条件

今回のサイネージでは、ストレージへ以下を保存する。

- Raspberry Pi OS
- Chromium 等の実行環境
- サイネージ Web アプリ
- 設定ファイル
- 天気・予定等のローカルキャッシュ
- アプリケーション / OS のログ
- Future で追加する写真等のローカルデータ

MVP では動画や大量の写真をローカル保存する予定はなく、時計・予定・天気・気温の表示が中心となる。
そのため、大容量・高スループットよりも、**長時間稼働時の耐久性、構成の単純さ、軽量性、低消費電力、十分な空き容量**を優先する。

選定条件を以下とする。

| 選定観点 | 条件・方針 |
|---|---|
| 容量 | OS・アプリ・ログ・キャッシュに十分な余裕を確保する |
| 耐久性 | 常時稼働に近い運用と継続的なログ書き込みを考慮する |
| 性能 | Chromium + Web UI の通常利用に支障がないこと |
| 消費電力 | 壁掛け一体型のため可能な限り小さいこと |
| 重量 / 厚み | 筐体への影響を最小化する |
| 配線 | 追加配線をできるだけ増やさない |
| 構成 | 部品点数が少なく、交換・復旧が容易であること |
| 拡張性 | Future の写真表示等にも一定の余裕を持たせる |
| 価格 | プロジェクト総予算 5〜6 万円を圧迫しないこと |

### 7.2 容量の検討

候補容量として 32GB / 64GB / 128GB を検討した。

| 容量 | MVP | ログ / キャッシュ | 写真保存 | 評価 |
|---|---|---|---|---|
| 32GB | ○ 十分実行可能 | ○ 管理すれば問題なし | △ 大量保存には不向き | 最小構成として成立する |
| **64GB** | **◎** | **◎ 余裕あり** | **○ 少量〜中程度なら対応可能** | **容量と価格のバランスがよい** |
| 128GB | ◎ | ◎ | ◎ | 現時点では余裕が大きく、用途に対して過剰気味 |

32GB でも Raspberry Pi OS、Chromium、サイネージアプリ、API キャッシュ、ログを保存して MVP を動作させることは可能と判断した。

一方、長期間の運用では OS 更新、パッケージ追加、ログ、キャッシュ等により使用量が増える。
また、Future では写真スライドショーも検討している。

そのため、初期費用を大きく増やさず空き容量に余裕を確保できる **64GB を採用容量**とする。

128GB は写真・動画を大量にローカル保存する構成では有効だが、現在はクラウド連携や必要データのみのキャッシュも想定しているため、MVP 時点では採用しない。

### 7.3 ストレージ方式の比較

Raspberry Pi 5 で利用可能な方式として、microSD と NVMe SSD を比較した。

| 項目 | microSD | NVMe SSD + NVMe Base |
|---|---|---|
| MVP に必要な性能 | **○ 十分** | ◎ 十分以上 |
| 読み書き性能 | ○ | **◎** |
| 書き込み耐久性 | 製品による | **◎ SSD により高耐久化可能** |
| 容量 | ○ | **◎** |
| 追加基板 | **不要** | 必要 |
| 追加配線 | **不要** | PCIe FFC が必要 |
| 重量 | **ほぼ増加なし** | Base + SSD + 固定部品分増加 |
| 厚み | **増加なし** | Pi 下部へ積層するため増加 |
| 消費電力 | **小さい** | 増加する |
| 筐体設計 | **容易** | Base / SSD / FFC のクリアランス設計が必要 |
| 学習要素 | ○ | **◎ PCIe / NVMe Boot 等を学べる** |
| 今回の用途への適合 | **◎** | △〜○ 性能面ではオーバースペック |

NVMe については **Pimoroni NVMe Base for Raspberry Pi 5** を利用する構成も検討した。

NVMe Base を利用すれば、Raspberry Pi 5 の PCIe を利用して高速な NVMe SSD を接続でき、ストレージ性能・容量・Linux / PCIe / NVMe に関する学習価値は高い。

一方、今回の完成形は壁掛け一体型を想定している。
NVMe Base を追加すると Pi の下側へ基板と SSD を積層するため、以下のデメリットが発生する。

- Base、SSD、スペーサー等による重量増加
- 完成時の厚み増加
- PCIe FFC の追加
- 消費電力の増加
- 筐体内部のクリアランス設計の複雑化
- 部品点数・コストの増加

また、NVMe Base を装着した Pi 5 は公式ケースには収まらない構成となり、専用ケースまたは自作筐体が必要になる。
今回も最終的には自作筐体を想定しているものの、**サイネージとして必要な性能を得るために筐体を複雑化する必要性は低い**と判断した。

MVP の主要な I/O は OS、Chromium、Web アプリ、設定、ログ、API キャッシュであり、NVMe の高い転送性能を活用する処理は予定していない。

したがって、NVMe は技術的・学習的には魅力があるものの、今回の製品要求に対してはオーバースペックと判断し、採用しない。

### 7.4 microSD の耐久性

一般的な microSD を OS 用ストレージとして長期間使用する場合、ログやキャッシュ等による継続的な書き込みによって NAND Flash の書き換え寿命が懸念となる。

そのため、通常用途向けカードではなく、継続的な書き込みを想定した **High Endurance 系 microSD** を優先する。

候補として以下を検討した。

**SanDisk High Endurance microSDXC 64GB**  
型番：**SDSQQNR-064G-GH3IA**

メーカーではドライブレコーダーやホームモニタリング等の継続記録用途を想定した製品として位置付けられている。
今回のサイネージでは映像を常時記録するのではなく、主な書き込みは OS、ログ、設定、API キャッシュであるため、想定される書き込み負荷は録画用途より小さい。

このことから、今回の長時間稼働用途に対して十分な耐久性を持つと判断した。

ただし High Endurance 製品を採用しても、ストレージ障害を完全に防止できるわけではない。
ソフトウェア側でも以下を考慮する。

- ログを無制限に蓄積しない
- systemd journal / logrotate 等でログ容量に上限を設ける
- API キャッシュに保存期間・容量上限を設ける
- ソースコードは GitHub で管理し、microSD の故障時に再構築可能にする
- 重要な設定データのバックアップ方法を検討する
- v1.0 でストレージ使用量を監視できるようにする

### 7.5 採用品

ストレージは以下を採用する。

| 項目 | 採用内容 |
|---|---|
| 方式 | **microSDXC** |
| 製品 | **SanDisk High Endurance microSDXC** |
| 容量 | **64GB** |
| 型番 | **SDSQQNR-064G-GH3IA** |
| 状態 | **✅ 採用** |

### 7.6 採用理由

**SanDisk High Endurance 64GB を採用する理由は以下の通り。**

1. **MVP に対して 64GB で十分な容量がある**  
   OS、Chromium、Web アプリ、ログ、キャッシュに加え、Future の写真表示にも一定の余裕を確保できる。

2. **長時間稼働に適した High Endurance 製品である**  
   通常の microSD より継続的な書き込みを考慮した製品を選ぶことで、ログ・キャッシュ等による耐久性リスクを下げられる。

3. **Pi 本体だけでストレージ構成が完結する**  
   NVMe Base のような追加基板、FFC、スペーサー等が不要である。

4. **軽量・薄型の壁掛け一体型という要求と相性がよい**  
   ストレージ追加による重量・厚み・筐体スペースの増加がほぼない。

5. **消費電力と部品点数を抑えられる**  
   NVMe SSD と比較して電源・筐体設計への影響を小さくできる。

6. **NVMe の性能を必要とする処理が MVP に存在しない**  
   今回のサイネージ用途では NVMe の大幅な I/O 性能向上を活用する場面が少なく、性能向上より構成の単純さを優先する。

### 7.7 実機確認事項

購入・構築後に以下を確認する。

- Raspberry Pi OS の実使用容量
- Chromium / サイネージアプリを含めた空き容量
- 長時間稼働時のログ増加量
- API キャッシュの使用量
- `df` 等によるストレージ使用率
- microSD の読み書き性能が UI 表示に影響しないこと
- OS 更新後も十分な空き容量を維持できること

これらを確認し、64GB では不足すると判明した場合のみ、128GB microSD または NVMe 等への変更を再検討する。

## 8. 電源・電源ケーブルの選定

### 8.1 電源要件

現在の主要構成から必要な給電条件を整理する。

| 機器 | 給電条件 | 備考 |
|---|---|---|
| Raspberry Pi 5 | **5V / 5A 級** | Active Cooler は Pi 5 の4ピンファンヘッダから給電 |
| Santek Display | **5V / 2A** | USB Type-C 給電 |
| Raspberry Pi Active Cooler | Pi 5 から給電 | 独立した AC アダプターは不要 |

単純合算では最大約35W級となるが、Pi 5 と Display では要求する給電条件が異なる。

当初は1台のマルチポートUSB電源から両方へ給電する方式も検討した。しかし、Pi 5 側で 5V / 5A を確実に供給しながら、別ポートから Display へ 5V / 2A を同時供給できる製品は選択肢が限られる。また、ポートごとの出力条件や同時使用時の電力配分も確認する必要がある。

そのため、電源を無理に1台へ統合せず、**Pi 5 と Display を独立給電し、外観上の配線をまとめる**方針とする。

### 8.2 Raspberry Pi 5 用電源

Pi 5 用として以下を比較した。

| 項目 | Raspberry Pi 公式 27W USB-C Power Supply | Switch Science 5.1V/5A USB-PD ACアダプター |
|---|---|---|
| Pi 5 向け 5.1V / 5A | **対応** | **対応** |
| Pi 5 公式品 | **○** | × |
| ケーブル | USB-C 固定 | USB-C 固定 |
| ケーブル長 | 約1.2m | 約1.2m |
| 国内での入手性 | ○ | ○ |
| 価格 | 約2,750円（調査時） | 約2,400円（調査時） |
| 評価 | **◎** | ○〜◎ |

価格差が小さく、Pi 5 + Active Cooler を長時間安定稼働させることを優先するため、Pi 5 用には公式電源を採用する。

**採用品：Raspberry Pi 公式 27W USB-C Power Supply（黒 / SC1418）**

### 8.3 Santek Display 用電源

Santek Display は USB Type-C から **5V / 2A** で給電する。

Pi 5 のような 5V / 5A の特殊な給電条件はないため、国内メーカーの PSE 適合品で、必要出力を満たすシンプルな AC アダプターを優先する。

**採用品：サンワサプライ ACA-IP87BK**

採用理由：

- 5V / 2A の要求を満たす
- 国内メーカー品である
- PSE 適合品として選択できる
- Display 用途では高価な USB PD / GaN 電源を必要としない
- USB ケーブル分離型のため、設置条件に合わせてケーブル長を選べる

### 8.4 設置高さと延長方針

サイネージは、壁コンセントから最大約 **1.8m の高さ**へ設置する可能性がある。

Pi 5 用公式電源の USB-C ケーブルは約1.2mであるため、設置位置によっては長さが不足する。

Pi 5 は 5V / 5A の大電流給電となるため、USB-C 側へ延長ケーブルを追加する方法は採用しない。必要な距離は **AC100V 側の延長コード**で補う。

AC 延長コードは家庭にある既存品を利用可能とし、今回のハードウェア購入対象・製品選定対象からは外す。

### 8.5 Santek Display 用 USB ケーブル

Pi 5 側の固定ケーブルが約1.2mであることから、Display 側は取り回しに少し余裕を持たせて **1.5m** とする。

**採用品：サンワサプライ KU-CA15BK**

| 項目 | 内容 |
|---|---|
| 端子 | USB-A → USB Type-C |
| 長さ | **1.5m** |
| 給電能力 | Santek の 5V / 2A 要求を満たすもの |
| 用途 | ACA-IP87BK → Santek Display の給電 |
| 状態 | **✅ 採用** |

### 8.6 ケーブルスリーブ

Pi 5 用 USB-C 電源ケーブルと Santek 用 USB-A → Type-C ケーブルは、壁面で別々に露出させず、1束にまとめる。

**採用品：サンワサプライ CA-SL13BK2 系 ケーブルスリーブ**

これにより、電気的には Pi 5 と Display の独立給電を維持しながら、外観上は1本の配線束として処理する。

### 8.7 筐体への要求追加

今回の配線方針から、筐体には以下の条件を追加する。

- Pi 5 用電源ケーブルと Display 用電源ケーブルを内部へ引き込めること
- 筐体下部または背面にケーブル通し用の開口を設けられること
- ケーブルやスリーブを無理に折り曲げないこと
- 開口部でケーブル被覆を傷つけない形状とすること
- 壁掛け時に配線が正面から目立ちにくいこと
- 壁とのクリアランスを考慮し、背面出し / 下部出しを筐体設計時に最終判断すること

### 8.8 採用構成

```text
サイネージ
├─ Raspberry Pi 5
│   └─ Raspberry Pi 公式 27W USB-C Power Supply
│      └─ 固定 USB-C ケーブル 約1.2m
│
└─ Santek Display
    └─ USB Type-C
       └─ サンワサプライ KU-CA15BK 1.5m
          └─ サンワサプライ ACA-IP87BK 5V/2A

Pi用ケーブル + Display用ケーブル
        ↓
サンワサプライ CA-SL13BK2 系スリーブで1束化
        ↓
必要に応じて手持ちのAC延長コード
        ↓
壁コンセント
```

### 8.9 採用理由

電源・配線は以下の考え方で決定した。

1. **Pi 5 の安定性を優先する**  
   5V / 5A を確実に供給できる Raspberry Pi 公式27W電源を使用する。

2. **Display は要求に対して過剰な電源を使用しない**  
   5V / 2A を満たすシンプルな国内メーカー品を使用する。

3. **マルチポート電源への統合を必須としない**  
   Pi 5 の 5V / 5A と Display の 5V / 2A を同時に確実に満たす製品を探すより、独立給電の方が構成と責任範囲が明確になる。

4. **配線の見た目は電源統合ではなくスリーブで解決する**  
   2本のケーブルを1束化し、壁掛け時の外観を整える。

5. **長さ不足はAC側で補う**  
   Pi 5 の5V側を延長せず、必要に応じて既存のAC延長コードを使用する。

6. **筐体設計へ配線条件を引き継ぐ**  
   下部または背面に配線口を設け、ケーブルを筐体内部へ自然に引き込める構造とする。
