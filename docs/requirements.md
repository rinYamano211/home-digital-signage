### MVP以降の扱い（既存方針と追加要求）

- v1.0：壁掛け・専用筐体・配線整理、時間帯によるコンテンツ切替、更新の容易さ、ストレージ使用量確認。
- Future：写真・スライドショー、コンテンツON/OFF・順序・表示時間のユーザー変更、Web管理画面、音声、クラウド管理、センサー、画面ON/OFF、縦横・複数画面サイズ対応、CI/CD。
- Future（R-01追加）：秒表示のON/OFFを含む時計表示のカスタマイズ。MVPから時刻を秒まで扱い、将来の秒表示を妨げない。その他のカスタマイズ項目は未検討。
- Future（R-02・R-11追加）：予定の表示形式の選択、画面に表示するもの・配置のカスタマイズ。今日の予定はMVPでリスト表示とし、時間軸表示と形式の選択は将来対応とする。
- Future（R-03追加）：天気・気温の対象地点を追加し、複数地点を扱えるようにする。MVPは自宅周辺の1地点。
- Future（追加）：ニュース、株価、ウィジェット型レイアウト、コンテンツ追加・並べ替え・サイズ変更、異常時キャッシュを残す／残さない設定（R-11）。
- MVPの動作設定は本体と分離して保持する。切替順はR-04の固定順、表示時間は実機で調整する固定値とし、利用者による変更機能・設定UIはFuture（R-08）。
- Out of Scope：タッチ操作。
- MVPは机上検証を許容する。筐体詳細設計は実物到着後に進める。
- 外部の予定・天気APIを利用することと、自作のクラウド管理基盤を作ることは区別する。

## 4. 要件ごとの検討

### R-01：時計・日時表示

#### 条件・検討事項

- 時計・日付・曜日を常時確認できること。
- 将来、秒表示をカスタマイズできること。
- 表示内容・時刻形式・内部で扱う時刻の粒度を決める。
- 配置・大きさはIssue #5、取得・同期方法と更新周期はIssue #3・#4で検討する。

#### 検討中に出てきた課題や懸念

- 時刻を分単位の情報だけで扱うと、秒表示の追加時に取得処理の変更が必要になる。
- 当初は時刻未同期・日付変更・タイムゾーンを未決定としていた。誤った時刻の表示や日付基準の不一致を避けるため、下記の基本動作を確定した。
- 秒まで扱うことは、外部APIへの毎秒アクセスを意味しない。

#### 案・候補

| 比較項目 | 案 |
|---|---|
| 表示情報 | 時刻のみ / 日付・曜日も表示 |
| 時刻形式 | 24時間表記 / 12時間表記 |
| 秒表示 | 時・分 / 時・分・秒 |

#### 決定案とその理由

| 項目 | 決定案 | 理由 |
|---|---|---|
| 常時表示 | 時刻＋日付＋曜日。コンテンツ切替中も維持 | 掛け時計として日付と時刻をいつでも確認するため |
| 時刻形式 | 24時間表記 | MVPの表示形式を統一するため |
| 秒 | MVPでは非表示 | 簡潔な表示にするため |
| 表示例 | `9月12日（土） 14:30` | 日付・曜日・時分をまとめて確認するため |
| 時刻の扱い | 秒まで扱える時刻を取得・利用する | 表示形式と時刻情報を分け、将来の秒表示に対応するため |
| カスタマイズ | 秒表示のON/OFFはFuture | MVPの表示仕様を絞りつつ拡張できるようにするため |

#### 時刻未同期・日付変更・タイムゾーンの基本動作

| 場面 | 決定した動作 | 理由 |
|---|---|---|
| 時刻未同期 | 正しい時刻を取得できていない場合はローカル時刻を表示せず、未同期と分かる状態を表示する | 誤った可能性のある時刻を通常の時計として見せないため |
| 起動と同期完了 | 同期完了を基本画面起動の前提にせず、同期後は利用者操作なしで通常の時計表示へ移行する | 起動を妨げず、正しい時刻が利用でき次第表示するため |
| 日付変更 | 日付・曜日と「今日」を基準とする予定・天気を自動的に新しい日へ切り替える。利用者操作は不要 | 表示対象を当日に一致させるため |
| 日付またぎ予定 | 前日から継続中の予定は終了まで表示対象とする | 日付が変わっても継続中の予定を見失わないため |
| タイムゾーン | 時計・日付・「今日」の判定など時間依存処理は共通のタイムゾーンを使用し、MVPの設定値として保持する。初期運用は日本標準時を想定 | 時計と予定・天気の日付基準を揃えるため |

未同期時の具体的な文言・アイコン・レイアウトはIssue #5へ引き継ぐ。
時刻同期方式、日付変更時の再取得・キャッシュ更新、OS設定・設定形式・利用ライブラリはIssue #3/#4で決定する。

### R-02 / R-10：予定の取得元

#### 条件・検討事項

- 現在利用している予定管理アプリへの依存はなく、新規サービスを利用できる。
- API取得が容易で、他サービスとの連携が取りやすいこと。
- 採用サービス、対象カレンダー、登録・編集を行う場所、読み取り範囲を決める。

#### 検討中に出てきた課題や懸念

- 認証情報の更新・失効を含めた継続運用が必要。
- 取得する期間・項目は表示モードの要件と整合させる必要がある。
- 取得異常時の表示方針はR-07に定義。取得間隔・有効期限の暫定値は同節の表を正本とし、API条件確認後に確定する。
- 認証方式と継続運用の設計はIssue #3・#4で具体化する。

#### 案・候補

| 候補 | 評価 |
|---|---|
| Googleカレンダー | 第一候補。期間指定・繰り返し予定の取得に対応し、Calendar APIやApps Scriptで連携を作れる |
| Outlookカレンダー | Microsoft Graphで期間内の予定を取得でき、Microsoft系サービスとの連携を重視する場合に候補 |

利用方法の案：
- 専用カレンダー1つを対象にする。
- 登録・編集はカレンダーサービス側で行い、サイネージは定期取得・読み取り表示に対応する。
- 取得異常時のキャッシュ利用と更新状態表示はR-07の決定内容に従う。

専用カレンダーは表示対象を選びやすく、外部サービスでの登録・編集は予定入力画面の自作を省ける。

#### 決定案とその理由

選定基準は「API取得と他サービス連携の容易さ」とする。既存サービスへの移行制約がなく、今回の用途と将来拡張への適合を重視できるため。
採用サービス・認証方式はIssue #4で正式選定し、対象カレンダー・専用カレンダー方式・読み取り専用の運用はIssue #3/#4で具体化する。これらは取得・表示要求を実現するための設計・選定事項とする。

参考資料：
- [Google Calendar：予定一覧取得](https://developers.google.com/calendar/api/v3/reference/events/list?hl=en)
- [Google Apps Script：Calendar Service](https://developers.google.com/apps-script/reference/calendar)
- [Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)
- [Microsoft Graph：calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0)

### R-02：予定の表示内容・MVPの範囲

#### 条件・検討事項

用途に応じたFutureの表示形式候補として、次の5種類を検討した。すべてをFutureの必須仕様として確定するものではない。

| モード | 表示する情報 | 検討事項 |
|---|---|---|
| 1か月カレンダー | タイトルと時間 | 当月か任意月か、週の始まり |
| 1週間 | タイトルと時間 | 暦週か今日から7日間か、週の始まり、画面形式 |
| 今日・明日 | 月表示より詳細な情報 | 場所・説明などの詳細項目 |
| 今日 | 当日の全予定。基本は開始時刻とタイトル、日付またぎは終了時刻も表示 | 具体的なレイアウト、件数超過・日付またぎの表記 |
| 直近前後3〜4時間 | 現在時刻の前後にある予定 | 前後それぞれ3時間か4時間か、可変にするか、日またぎ |

表示形式を選べる将来像を持ちつつ、MVPは今日の予定のリスト表示のみを対象とする。時間軸表示はFuture候補として残す。

#### 検討中に出てきた課題や懸念

- 1280×800の画面で月・週表示のタイトルと時間を読み取れるか。
- 予定件数が多い場合やタイトルが長い場合の表示。
- 今日の予定は通常の終了時刻を省くが、取得可能な終了時刻は内部で保持し、進行中・終了済みの判定に使う。他の表示モードの時刻表現は未定。
- 今日の予定の終日別枠・予定なしの文言・終了済みの薄表示は決定。日付またぎの基本動作は下記で決定。繰り返し・重複、進行中や終了済みの判定境界、終了時刻を取得できない場合、他モードでの扱いは設計で具体化する。
- 表示モードに応じた取得期間・項目・キャッシュ範囲の設計。
- 予定取得と表示形式を分け、同じ予定を複数の表示形式で利用できる構成を検討する。

#### 案・候補

当初は当日の全予定・当日の未終了予定・今日と明日の予定を比較した。その後、月・週・直近時間帯も含む5種類へ検討範囲を広げた。

MVPで比較した候補：

| 候補 | 利点 | 検討点 |
|---|---|---|
| 週表示 | 数日先を含めて予定を見渡せる | 7日分の視認性、週の範囲、件数超過 |
| 今日の予定 | 1日の流れを確認でき、文字を大きくしやすい | 一覧か時間軸か、各予定の状態表示 |

今日の予定を先に実装する案では、1日分に絞って予定取得・表示・コンテンツ自動切替を検証する。
表示内容は、当日の全予定を開始・終了時刻とタイトルで時刻順に並べ、終日予定を別枠にする案を検討した。基本表示内容は下記の決定内容にまとめる。

#### 決定案とその理由

Futureの表示形式候補として、月・週・今日と明日・今日・直近前後3〜4時間を検討している。MVPは「今日」のリスト表示のみとする。
以前は5種類を最終的な表示要求としていたが、将来の必須仕様ではなく選択肢として整理し直した。
月・週の見通し、今日・明日の詳細、1日の流れ、現在時刻付近の予定を用途に応じて確認するため。
検討案では月・週はタイトルと時間に絞り、詳細表示では情報量を増やすことを想定した。

MVPは当日の全予定をリスト表示する。参考画像の予定欄のように、予定情報または予定がないことを簡潔に読める表示を目指す。基本仕様は以下とする。

#### 今日の予定：決定した表示内容

| 項目 | 決定内容 | 理由 |
|---|---|---|
| 対象 | 当日の全予定。前日以前から当日へ続く予定も含む | 終了済みを含む1日の流れと、日付変更後も続いている予定を確認するため |
| 表示形式 | MVPは当日の予定をリスト表示 | 予定の時刻とタイトルを順に確認しやすくするため |
| 表示情報 | 原則は開始時刻＋タイトル。日付またぎのみ終了時刻も表示 | ひと目で把握する情報量を優先し、日付またぎの継続時間は分かるようにするため |
| 並び順 | 時刻順。終日予定は別枠 | 1日の順序を把握し、時間指定のない予定を区別するため |
| 終了済み | 薄く表示 | 履歴を残しつつ、未終了の予定と区別するため |
| 進行中 | 強調表示 | 現在の予定を見つけやすくするため |
| 予定なし | 「本日の予定はありません」 | 予定がない状態を明示するため |

レイアウトや色・強調方法はUI設計で具体化する。薄く表示する場合も読み取れることを条件とする。
取得失敗は「本日の予定はありません」と区別し、キャッシュの有効性に応じてR-07の表示に従う。

#### 表示時刻の変更経過と日付またぎ

以前は開始・終了時刻とタイトルを表示する方針だったが、通常の終了時刻を省く方針へ変更した。
サイネージとして一目で把握する情報量を優先し、終了時刻の常時表示の必要性は低いと判断したため。
表示を省いても、終了時刻を取得可能であれば内部で保持し、進行中・終了済みの判定に利用する。

日付をまたぐ予定は例外として終了時刻も示す。例えば9/13 23:00〜9/14 01:00の予定は、9/14 00:30にも現在の予定として扱う。
「翌01:00まで」等の具体表記はIssue #5で決め、表示日の違いによって終了日を誤認させないようにする。

#### 表示形式の変更経過と将来対応

今日の予定は、Futureで時間軸表示とリスト表示を選べる案を残す。
時間の流れを確認する表示と、予定を順に読む表示を使い分けるため。
当初はMVPを時間軸表示で検討した。その後、予定をリストで読みたいという表示イメージに合わせ、MVPをリスト表示へ変更した。時間軸表示と表示形式の選択は将来対応とする。
予定なしの文言も、当初の「今日の予定はありません」から「本日の予定はありません」へ変更した。

月・週など他の対象期間でもリスト表示を利用するか、表示項目や日付の区切りをどうするかは未決定。

#### 将来の時間軸表示で検討する事項

- 表示時間帯：0〜24時全体、生活時間帯の固定範囲、予定に合わせた範囲など。
- 当日の全予定を対象とする方針と、画面に収まる時間軸の範囲を両立する方法。
- 重複予定の配置、短時間予定のタイトル・時刻の視認性。
- 日またぎ予定の表現、現在時刻の位置、終日予定の別枠の配置。
- 全件を一画面で見せるか、収まらない場合にどのように表示するか。

#### 予定の近さに応じた表示サイズ

予定一覧の自動ページ切替を比較案として検討したが、採用しない。自動切替はコンテンツ間を基本とし、一覧を読むための待ち時間を増やさない。

進行中の予定と次に始まる1件を大きく表示し、それより後の予定は小さめに表示する。表示上の工夫はIssue #5のUI検討で具体化する。
時刻順と当日の全予定を対象とする方針を維持しながら、今必要な情報を見つけやすくする。

| 対象 | 表示方針 | UI検討事項 |
|---|---|---|
| 進行中 | 大きく、強調して表示 | 同時に複数ある場合 |
| 次に始まる1件 | 進行中の予定と合わせて大きく表示 | 同時刻に複数開始する場合の1件の選び方 |
| それより後の予定 | 小さめに表示 | 一定サイズか段階を設けるか、詳細情報として判読できる最小サイズ |
| 終了済み | 小さめ・薄く表示 | 小さくする案は未決定。薄く表示する方針は決定済み |
| 終日予定 | 別枠で表示 | 大きさと強調の有無 |

大きくする対象は「進行中の予定＋次に始まる1件」とする。文字サイズ、大小の段階、余白、配置、重複時の見せ方はIssue #5で検討する。
時刻の経過による予定状態の更新と、一覧の自動ページ切替は分けて考える。

**課題・懸念**

- 大小を付けても、予定が多い日には全件が収まらない可能性がある。
- 「当日の全予定」と最小文字サイズを両立するため、最大件数や超過時の扱いを別途決める。
- 非表示や件数だけの表示への置き換えは、現時点では決めない。
- 重複予定の配置や、同時刻に開始する予定の選び方をUI検討で具体化する。

#### UI検討への引き継ぎ（Issue #5）

- 画面内の最大表示件数と、全件が収まらない場合の表示方法。
- 長いタイトル、重複予定、日またぎ予定の表現。
- 終日予定の別枠、終了済み・進行中の見せ方の具体化。

#### 画面イメージ

参考画像では、大きな時計・日付の隣に予定欄があり、予定なしを「本日の予定はありません」と表示している。
予定欄と空の状態の見せ方をUI設計の参考にする。画像内の秒表示・フリップ時計・背景写真・天気の同時配置は、この段階の採用仕様には含めない。
時計のMVP仕様は日付・曜日＋24時間表記の時分、秒非表示を維持する。コンテンツ自動切替の方針も維持する。

### R-03：屋外気温・天気予報・降雨見込み

#### MVPで表示する情報

| 情報 | 表示内容 |
|---|---|
| 現在の天気・気温 | 天気アイコンとAPIから取得した現在の屋外気温 |
| 当日の天気 | 1時間ごとの天気アイコン・気温・降水確率 |
| 週間天気 | 今日を含む7日間の天気アイコン・最高／最低気温・降水確率 |
| 短時間の降雨情報 | 降り始め・降り終わりまでの見込みを分単位で表示 |

室温計測ではなく屋外気温を対象とする。雨雲レーダー画像・地図の表示はMVPでは行わない。
R-03の要件定義は完了。降雨情報もMVPの表示要求に含め、実現可能性はIssue #4で検証する。採用APIや対応範囲を既に検証済みという意味ではない。

#### 比較した案と判断理由

当日予報は1時間ごとと3時間ごとを比較し、時間帯ごとの変化を確認するため1時間ごとを採用した。
週間天気は数日先の見通しを確認するため、今日を含む7日間とする。
当日の最高・最低気温や週間の日付・曜日は補助項目として挙がったが、追加の要否はIssue #5で表示密度と合わせて検討する。

降雨見込みは時間単位と分単位を比較し、より細かくタイミングを把握するため分単位を採用した。
「あと約20分で雨の見込み」「あと約30分でやむ見込み」などを想定するが、これは表示例であり予測精度の保証ではない。
短時間降雨予測に対応したデータを用いる。1時間単位の予報を単に分換算しただけでは要件を満たさない。

#### 対象地点の検討経過と決定

市区町村・郵便番号・緯度経度などの指定方法を検討した。
MVPは自宅周辺など任意の1地点を設定して使い、可能な限りピンポイントに指定できることを希望する。
家庭用として必要な地域に絞りながら、地域全体の代表値だけに限定しないため。

指定方式は現時点では固定しない。緯度経度指定に加え、気象庁のメッシュデータ等を利用する可能性も含め、提供元の仕様を調査してIssue #4で決める。
Futureでは地点を追加し、複数地点を扱えるようにする。登録・選択・表示方法、地点の自動切替は未決定。

#### 気象データ提供元の候補と選定条件

正式選定はIssue #4で行う。少なくとも気象庁、OpenWeather、Open-Meteo、Tomorrow.io、日本気象協会、ウェザーニューズを調査対象とする。
これらは調査候補であり、必要な機能が利用可能と確認したものではない。

| 比較観点 | 確認する内容 |
|---|---|
| 情報の充足 | 現在・当日・7日間・降雨開始／終了の情報を取得できるか |
| 対象地域・地点粒度 | 日本国内の対応範囲、任意地点の指定方法と空間粒度 |
| 短時間降雨予測 | 時間・空間粒度、予測可能期間、更新頻度 |
| データ取得・処理 | API・データ形式、認証方法、Raspberry Pi上での実装容易性 |
| 運用条件 | 利用料金、レート制限、利用規約、情報ごとの更新頻度 |

単一APIでの取得に限定しない。通常の天気と短時間降雨情報で異なる提供元を組み合わせる案も比較する。
必要な情報と粒度を満たすことを優先し、複数提供元を使う場合の責務分離はIssue #3へ引き継ぐ。

### R-04 / R-11：コンテンツ自動切替・カスタマイズ

#### MVPの切替単位と固定表示

時計・日付・曜日は常時固定し、切替の影響を受けない。
MVPの通常時の切替順は、**今日の予定 → 今日の天気 → 週間天気 → 今日の予定**の繰り返しで固定する。

| 切替単位 | 含める情報 |
|---|---|
| 今日の予定 | R-02の当日の予定リスト |
| 今日の天気 | 現在の天気・屋外気温、当日の時間別天気、短時間の降雨情報 |
| 週間天気 | 今日を含む7日間の予報 |

現在天気・気温・時間別天気・降雨情報を別々の切替コンテンツにはしない。
細分化すると巡回する画面が増え、見逃した情報を再び見るまでの待ち時間が長くなるため、関連情報を「今日の天気」にまとめる。
週間天気は情報量・性質が異なるため独立させる。

以前は「予定・天気・気温など」として切替単位と順序を未決定にしていたが、上記3単位へ具体化した。
予定の表示モードを自動巡回する案や、選択したモードだけを巡回する案も検討したが採用しない。
予定一覧の自動ページ切替も採用しない。予定形式の選択はFutureとし、MVPではリスト表示を使う。

#### 表示時間

各コンテンツを一定時間表示して切り替える。MVPでは固定値を持つが、具体的な秒数は今は確定しない。
実装時に初期値を設定し、10.1インチ実機で情報量・読みやすさ・切替速度を確認して調整する。
表示時間を設定値として扱える構造は想定するが、利用者が表示時間を変更する機能や設定UIはMVPに含めない。

#### 通信・取得異常時のローテーション

異常が起きたコンテンツを一律に残す／飛ばすとはせず、情報種別ごとの鮮度と、その情報に引き続き利用価値があるかで判断する。

| 情報 | 判断方針 |
|---|---|
| 今日の予定・週間天気 | 有効なキャッシュがあり、引き続き利用価値がある場合はローテーションに残す |
| 現在の天気・気温、時間別天気、降雨情報 | 鮮度への依存が大きいため、キャッシュの鮮度・有用性を評価する。ただし一部の取得失敗で正常・有効な情報が残る「今日の天気」全体を除外しない。全情報が利用不可の場合の扱いは設計で具体化する |

表示するキャッシュにはR-07の更新状態・最終更新日時の注記を適用し、有効期限を超えた情報は表示し続けない。
MVPでは利用者による異常時動作の変更機能は持たず、情報種別ごとの鮮度・有用性に基づいて扱う。具体的な判定条件・状態管理はIssue #3で設計する。
R-07の、有効なキャッシュのみ表示可能で期限切れキャッシュは表示しない原則を優先する。

データの表示状態（R-07）と、切替単位のローテーション参加可否は分けて扱う。
「今日の天気」等の複合コンテンツは、一部の情報だけ取得に失敗しても、正常な情報または有効なキャッシュが残っていればコンテンツ自体を巡回に残し、表示を継続する。情報単位の扱いはR-07に従う。
以前は部分取得失敗時にコンテンツ全体を残す条件を設計上の課題としていたが、上記の基本動作を確定した。
以下は後続Issueで具体化する。

- Issue #5：取得失敗した領域の文言・位置・空き領域の扱い。
- コンテンツを除外した場合や全コンテンツが除外対象になった場合の、取得失敗状態の伝え方。
- 取得成功後に通常表示・ローテーションへ自動復帰する方法。

除外を理由に古い情報を表示したり、時計や正常な別コンテンツまで停止させたりしない。
異常表示の具体的な位置・表現はIssue #3/#5で決める。

### R-05：視認性

#### 検討した条件と判断

当初の「離れても確認できる大きな文字」を、情報ごとの視認優先度と約3mの利用条件へ具体化する。
すべての情報に同じ視認距離・文字サイズを要求すると情報量との両立が難しいため、日常の中で自然に把握したい主要情報と、意識して確認する詳細情報を分ける。

| 対象 | MVPの視認性要件 |
|---|---|
| 時計 | 約3m離れても明確に時刻を判読できることを必須とする |
| 現在気温・現在の天気 | 約3mから概要を把握できるよう主要情報として大きく表示し、凝視せず目に入りやすいことを重視する |
| 今日の予定・時間別天気・降雨情報・週間天気 | 意識して画面を見た際に実用的に判読できることを重視し、主要情報より小さい表示を許容する |

現在気温・現在天気の要件は「今日の天気」が表示されている間に適用する。常時固定する情報は時計・日付・曜日であり、天気を常時表示へ変更するものではない。
詳細情報へ主要情報と同じ距離・大きさの条件は課さない。

Issue #13で10.1インチ・1280×800の実機を使い、時計の約3mからの判読性、現在気温・天気の視認性、詳細情報の実用的な判読性を確認する。

### R-07：取得異常・キャッシュ・データ鮮度

#### 条件と検討経過

通信断やAPI障害があっても、正常なコンテンツと時計を継続し、有効なキャッシュの利用を可能にする。異常時の巡回への参加可否はR-04に従う。一方で、有効期限を過ぎた古い情報を現在の情報として表示しない。
当初は取得済み情報と最終更新日時を表示する方針を検討した。その後、正常時・取得異常時・キャッシュの有効性に応じて表示を分ける方針へ具体化した。

**通信状態とデータ鮮度は別の状態として扱う。**
通信断直後でもキャッシュが有効な場合がある。一方、ネットワークに接続できていてもAPI障害などで取得できず、データが古くなる可能性があるため。

取得周期とキャッシュ有効期限も別の条件とする。取得周期は更新を試みる間隔、有効期限は保存済み情報を利用できる期間として、情報種別ごとに設定する。

#### 決定した動作

| 状態・項目 | 決定内容 | 理由 |
|---|---|---|
| 正常時 | 通常表示。キャッシュ利用中の表示や最終更新日時は表示しない | 通常利用時の表示を簡潔にするため |
| 取得異常＋有効なキャッシュあり | キャッシュを表示し、更新できていない状態と最終更新日時を表示 | 利用可能な情報を残しつつ、更新できていないことを伝えるため |
| 取得異常＋キャッシュ期限切れ | 古い情報を表示せず、「情報を取得できません」等の取得失敗状態を表示 | 古い情報を有用な情報として見せ続けないため |
| 初回未取得 | キャッシュがないため取得失敗状態を表示 | 情報がない状態を明示するため |
| 通信復旧 | ユーザー操作なしで取得を再開し、取得成功後に通常表示へ戻る | 手動復旧を不要にし、実際の取得成功をもって異常表示を解除するため |
| データ鮮度 | 情報種別ごとにキャッシュ有効期限を設定 | 情報によって古さの許容範囲が異なるため |
| 取得周期 | 情報の変化速度に応じて情報種別ごとに設定 | 必要な鮮度と取得負荷を両立するため |
| 最終的な数値 | 利用APIの更新頻度・レート制限・費用を確認後に確定 | API側の条件に適合する運用にするため |

この表は情報ごとの表示状態を定める。ローテーションに残すかどうかはR-04で別に判断し、除外時も取得失敗状態の伝え方を設計する。
有効なキャッシュを正常時の表示に利用しているだけでは、キャッシュ利用中の注記は出さない。
ネットワーク接続が戻っただけでは通常表示に戻さず、データの取得成功を条件とする。
予定の取得失敗は「本日の予定はありません」と区別する。キャッシュ期限切れや初回未取得では、予定の有無を断定せず取得失敗状態を表示する。

#### 部分取得失敗時の基本動作

複数種類の情報で構成されるコンテンツでは、取得に失敗した情報のみを取得異常の状態として扱う。
正常に取得できている情報と有効なキャッシュを利用できる情報は継続表示し、一部の取得失敗を理由にコンテンツ全体や正常な別コンテンツを停止しない。
失敗した情報に有効なキャッシュがあれば更新異常を示して表示し、期限切れならその情報部分のみ取得失敗表示とする。

| 「今日の天気」の例 | 表示 |
|---|---|
| 現在天気・気温：正常 | 通常表示 |
| 時間別天気：正常 | 通常表示 |
| 降雨情報：取得失敗＋有効キャッシュ | 降雨情報のキャッシュ＋更新異常・最終更新日時 |
| 降雨情報：取得失敗＋期限切れ | 古い降雨情報は表示せず、降雨情報部分のみ取得失敗状態 |

正常または有効な情報が残る「今日の天気」はR-04に従って巡回・表示を継続する。
失敗領域の具体的な文言・位置・空き領域の見せ方はIssue #5で決める。

#### MVPの暫定取得間隔・キャッシュ有効期限

**以下はMVPの暫定値であり、API選定前の確定仕様ではない。**

| 情報種別 | 暫定取得間隔 | 暫定キャッシュ有効期限 |
|---|---|---|
| 現在の天気・屋外気温 | 15分 | 2時間 |
| 1時間ごとの当日予報 | 30分 | 3時間 |
| 週間予報 | 6時間 | 12時間 |
| 降雨開始・終了見込み | 5分 | 30分 |
| 今日の予定 | 10分 | 6時間 |

取得間隔はデータ取得の周期であり、画面のコンテンツ切替間隔とは別に扱う。
降雨の5分取得は、分単位の表示要件や予測データ自体の時間間隔を変更するものではない。

#### 課題・設計時に具体化する事項

- キャッシュ有効期限の起点と、最終更新日時として扱う時刻（取得成功日時・APIの観測／予報更新日時等）の定義。
- APIから取得に成功しても元データが古い場合の鮮度判定。
- 日付変更や予報対象期間の終了時の扱い。R-01に従って新しい日へ切り替え、継続中の日付またぎ予定は終了まで対象とする。昨日だけの予定や対象期間を過ぎた予報を当日の情報として残さないための処理はIssue #3/#4で設計する。
- 降雨見込みのキャッシュを利用する際の「あと○分」の再計算と、予測時刻を過ぎた場合の扱い。
- 再取得の待ち時間、タイムアウト、API障害・認証失効・一部データのみ取得失敗した場合の具体的な復旧方法。
- 正確な異常時の文言、最終更新日時の表示形式・位置、初回取得処理中の表示はUI・設計で具体化する。

上記はIssue #3/#4/#5での具体化事項であり、Issue #2の要件残件ではない。暫定値に追加の数値条件を設けるものでもない。

### R-06：電源投入・再起動・異常終了からの自動復旧

#### 条件と検討経過

電源投入・Pi再起動・アプリ異常終了から自動復旧する基本方針を、起動時間と復旧時間の受け入れ条件まで具体化する。
MVPでは人手によるコマンド実行を必要とせず、Raspberry Piへの電源投入後にサイネージが自動起動すること。
外部APIの取得と基本画面の起動は分離する。

#### 受け入れ条件

| 場面 | 条件 |
|---|---|
| 電源投入 | Raspberry Piへの電源投入後、2分以内に時計領域を含む基本画面が自動表示される。時刻未同期時はR-01の未同期状態を表示 |
| 外部情報の未取得 | 予定・天気の外部API取得完了を待たず、基本画面を先に表示する。時計・日時はR-01に従い、未同期時はローカル時刻を表示しない |
| Raspberry Pi再起動 | ユーザー操作なしでサイネージが自動起動する |
| アプリケーション異常終了 | 異常終了から1分以内に自動的に再起動し、基本画面を復旧する |
| 復旧後の設定 | 保存済み設定を維持する |
| 一時的な通信・API障害 | サイネージ全体を停止せず、正常なコンテンツと時計の表示を継続する |

未取得の外部情報はR-07の取得失敗表示を適用し、基本画面自体の表示を妨げない。
時刻未同期でも基本画面の起動・復旧は待たせず、時計領域にはR-01の未同期状態を表示する。2分・1分の条件は基本画面に適用し、同期完了後に正しい時計表示へ自動移行する。

#### 決定理由と設計への引き継ぎ

家庭内で常設する用途では、電源投入や異常終了のたびに手動操作を必要としないことを優先する。
外部API取得と画面起動を分離することで、ネットワーク状態に依存せず基本画面を表示できるようにする。時計はR-01に従い、未同期時には未同期状態を示す。

プロセス監視・自動起動・自動再起動の具体方式はIssue #3/#4で決定する。
起動失敗・再起動失敗が繰り返される場合の扱いも設計で具体化する。

### R-09：長時間稼働・ログ・監視

#### 試験基準と検討経過

#### リソースの基準

#### 決定理由

72時間試験により、日付変更、定期データ取得、コンテンツ切替、キャッシュ更新、長時間のリソース利用を複数回確認する。
実装前に厳密なCPU使用率等の閾値を設定せず、実機測定をもとに必要な基準を追加する。
