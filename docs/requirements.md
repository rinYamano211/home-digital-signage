### MVP以降の扱い（既存方針）

- v1.0：壁掛け・専用筐体・配線整理、時間帯によるコンテンツ切替、更新の容易さ、ストレージ使用量確認。
- Future：写真・スライドショー、コンテンツON/OFF・順序・表示時間のユーザー変更、Web管理画面、音声、クラウド管理、センサー、画面ON/OFF、縦横・複数画面サイズ対応、CI/CD。
- Out of Scope：タッチ操作。
- MVPは机上検証を許容する。筐体詳細設計は実物到着後に進める。
- 外部の予定・天気APIを利用することと、自作のクラウド管理基盤を作ることは区別する。

## 4. 検討経過

### R-02 / R-10：予定の取得元（2026-09-12）

**論点**
現在は特定のアプリで予定を管理していない。今回のために新しいサービスを利用してもよい。
API取得が容易で、他サービスとの連携が取りやすいものを希望する（ユーザー確認済み）。

**比較した選択肢**

| 候補 | 評価 | 判断 |
|---|---|---|
| Googleカレンダー | 期間指定・繰り返し予定の取得に対応。Calendar APIやApps Scriptで連携を作れる | 第一候補として提案 |
| Outlookカレンダー | Microsoft Graphで期間内の予定を取得できる。Microsoft系の利用を重視する場合に候補 | 代替候補 |

**現在の判断**
選定基準は確定。Googleカレンダーの採用自体は未確定。
「他の要件検討へ進む」という依頼を、サービス採用の承認とは扱わない。

**提案した利用方法（未確定）**
- 専用カレンダー1つを対象にする。
- 予定の登録・編集はカレンダーサービス側で行う。
- MVPのサイネージ側は定期取得・読み取り表示のみとする。
- 当日の予定を表示し、通信断時はキャッシュと更新状態を表示する。

**理由**
予定入力画面を自作せずに、予定取得・表示というMVPの価値を検証できる。
専用カレンダーにより表示対象を選びやすくする。

**未決定事項**
- 採用サービス、専用カレンダー方式、読取専用の確定。
- 当日全件か、終了した予定を除くか、翌日以降も表示するか。
- 件名・開始/終了時刻・場所・終日予定の表示。
- 件数超過、長い件名、繰り返し、日またぎ、予定なしの扱い。
- 取得間隔、キャッシュ有効期限、日付変更、認証失効時の表示。
- 認証方式と継続運用の設計はIssue #3・#4で具体化する。

**比較時の参照資料**
- [Google Calendar：予定一覧取得](https://developers.google.com/calendar/api/v3/reference/events/list?hl=en)
- [Google Apps Script：Calendar Service](https://developers.google.com/apps-script/reference/calendar)
- [Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)
- [Microsoft Graph：calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0)

### R-01：時計・日付表示（2026-09-12、検討開始）

**論点**
時計を常時表示する方針は確定済み。何をどの形式で表示するかを決める。

**選択肢**
- 時刻のみ / 日付・曜日も常時表示。
- 24時間表記 / 12時間表記。
- 時・分 / 時・分・秒。

**提案（未確定）**
日付・曜日と24時間表記の時・分を常時表示する。秒は表示しない。
日本時間で利用する想定。表示位置・文字サイズはIssue #5で具体化する。

**理由**
離れた場所で日付・時刻を確認でき、秒表示による細かな変化を抑えられる。

**残件**
ユーザーの表示希望、日付書式、時刻未同期・日付変更時の動作。
